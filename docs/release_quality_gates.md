# Phase 34 - Regression Coverage and Release Quality Gates

The project is still **version 0.1.0, Unreleased**. These gates are evidence for
its current state, not a promise of production readiness or stable ABI.

## Reproducible verification entry points

Run from the repository root on Fedora or Linux with GCC, Clang, Python 3,
`make`, and (for the coverage probe) GNU `gcov` installed:

```sh
make quality-gate-test
make quality-quick
make coverage-smoke
make quality-release
```

`make quality-quick` runs `tools/quality_gate.py --profile quick --compiler gcc`.
It **starts with `make clean`**, builds with strict warnings, exercises targeted
admission/ingress/failure invariants, verifies staged static-library consumers,
documentation, version and CI contracts, and runs the gate's own unit tests.

`make quality-release` starts clean, builds with strict C11 warnings, runs
**all existing functional regression tests**, invokes both static analyzers
and executes the ASan/UBSan concurrent audit. It does *not* run long repeated
performance measurements, create tags or publish releases. On systems where
sanitizers cannot run, the command fails rather than treating the attempted
check as a pass. A successful release gate is a preflight check, not formal
proof of correctness.

`python3 tools/quality_gate.py --profile quick --compiler clang` repeats the
quick checks with Clang. The clean-first rule avoids accidental reuse of
GCC-built objects when switching compilers.

## Coverage probe

```sh
make coverage-smoke
cat build/coverage/gcov_summary.txt
less build/coverage/token_bucket.c.gcov
```

This builds **only** `tests/test_token_bucket.c` + `src/token_bucket.c` using
GCC `--coverage` at `-O0` and calls `gcov -b`. The result is an observed
line/branch-coverage measurement for the sequential token-bucket *module*,
not an estimate of project-wide coverage. Coverage measures which code was
executed, not whether its assertions are meaningful. The goal of the probe is
reproducible instrumentation and a positive coverage sanity check, not a
fragile global percentage threshold.

Everything generated by the probe is stored under ignored `build/coverage/`.
It is never staged as source or included in the downloadable repository ZIP.

## Fail-closed semantics

The runner calls `make` with an argument list and does not invoke a shell.
It checks that both `make` and the selected compiler are available, that a
`Makefile` exists, and that **each subprocess returns zero** before its per-step deadline (180 seconds for quick checks and 900 seconds for release checks by default). A failed check
stops later steps and exits nonzero. A missing program, launch error or deadline expiry also
exits nonzero. Use `--timeout-seconds N` for a different positive per-step limit;
a timeout is a failure, never a pass. The parent process may need additional
manual cleanup if a child starts its own long-running subprocesses. Unit tests simulate failed commands and missing tools to verify
this behavior.

The release profile selects existing Make targets; it doesn't duplicate the
underlying production tests. The `quality-gate-test` target itself is included
in the general `make test` dependency list, so the quality gate's reliability
is checked during normal CI too.

## Evidence and limits

| Layer | Primary gate | What it establishes | What it does not prove |
|---|---|---|---|
| Strict compile | `make all` | Warnings not silently ignored | Correctness |
| Functional | `make test` | Deterministic tests and observed concurrent scenarios | All possible interleavings |
| Static analysis | `make static-check` | GCC and scoped Clang analysis pass | Absence of all bugs |
| Sanitizers | `make audit-asan` | No detected errors in the exercised run | Race freedom or full memory safety |
| External consumer | `make package-test` | Installed-header/archive consumer works | ABI stability |
| Coverage probe | `make coverage-smoke` | Sequential token-bucket lines were exercised | Project-wide coverage or good assertions |

Long workload sampling (`make scaling-report`, `make mutex-compare-report`, etc.)
is deliberately kept **outside** this release-quality gate. Those commands
measure performance under noisy operating-system scheduling and may be rerun
separately for a performance report.

## CI and release policy

The existing `.github/workflows/ci.yml` continues to run GCC, Clang,
static analysis and sanitizer jobs. Hosted GitHub Actions must still be
confirmed from the actual repository's Actions tab; local testing doesn't
prove the hosted workflow ran. This phase does not add a Git tag, bump 0.1.0,
or declare a released artifact.

## Troubleshooting

1. **`gcc: command not found`** - install GCC through your package manager.
2. **`clang: command not found`** - install Clang or choose `--compiler gcc`.
3. **`gcov: command not found`** - install GCC's coverage utilities.
4. **ASan cannot start** - inspect the runtime/toolchain; do not convert its
   failure into a reported pass.
5. **A long benchmark hangs** - benchmark reports are separate from this
   gate; never suppress a failing required regression check.
6. **Changing compilers** - run a clean build between GCC and Clang. The gate
   does this automatically.

## Interview reasoning

The main engineering lesson is that a portfolio project's credibility depends
on reproducible failure behavior and traceable verification evidence, not just
on a benchmark headline. A pass is only as meaningful as the checks executed,
and a coverage percentage is only interpretable with a clear denominator.
